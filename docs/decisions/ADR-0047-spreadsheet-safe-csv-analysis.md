# ADR-0047: Spreadsheet-safe CSV analysis

**Status:** Accepted

## Context

The [export contract](../08-ingestion-and-export.md#export-contract) includes CSV analysis downloads.
Tabular snapshots can contain identifiers such as `=1+1`; exported text must not become a spreadsheet
formula. CSV quoting escapes delimiters and quotes but does not itself prevent formula evaluation.
Canonical identifiers, immutable scientific outputs, source artifacts, and existing exports must remain
unchanged.

[OWASP's CSV injection guidance](https://owasp.org/www-community/attacks/CSV_Injection) recommends
quoting and escaping fields with a leading apostrophe as a text marker. It identifies `=`, `+`, `-`,
`@`, tabs, carriage returns, line feeds, and locale-dependent full-width formula characters as hazards.
It also warns that Excel can remove escape characters on CSV save/reopen, and that no encoding is
universally safe across spreadsheet applications. Its alternative tab prefix is Excel-specific rather
than a portable text-cell contract.

## Decision

Apply this policy only when serializing newly generated CSV analysis output:

1. Keep the existing UTF-8 encoding, comma separator, LF record terminator, column names/order, and
   empty optional cells. Quote every CSV cell with double quotes and double embedded double quotes.
2. Prepend exactly one ASCII apostrophe (`'`, U+0027) to any nonempty text cell whose first character
   is `=`, `+`, `-`, `@`, their full-width equivalents `＝`, `＋`, `－`, `＠`, Unicode whitespace
   (`str.isspace()`), or a Unicode control/format character (general category `Cc` or `Cf`). This
   conservatively covers tabs, CR/LF, NUL, DEL, C1 controls, non-breaking spaces, zero-width formatting,
   and BOM (U+FEFF), even when no formula follows the prefix. Preserve the complete original string
   after the apostrophe: do not trim, normalize, replace, or remove characters.
3. Apply the same serializer helper to every data cell, including all free-text columns (`tei_id`,
   `evidence`, `resp`, and `cert`). Closed labels, tiers, and boolean text remain unchanged because
   their values do not start with hazardous characters. Leave ordinary text, including original
   apostrophe-leading text, unchanged.
4. Support LibreOffice Calc's explicit Text CSV import: UTF-8, comma separator only, double-quote
   string delimiter, **Format quoted field as text** enabled, **Evaluate formulas** disabled,
   **Trim spaces** disabled, and **Merge delimiters** disabled. Select **Text** for all columns
   to avoid identifier/date/number coercion. These settings follow the
   [official Text Import documentation](https://help.libreoffice.org/latest/en-US/text/shared/00/00000208.html).
   Spreadsheet defaults, other products, copying cells into formula contexts, and CSV save/reopen
   are outside this supported workflow; never claim universal or repeated-save safety.
5. Keep JSON as the lossless machine-readable result export. The CSV parser sees the protective
   apostrophe as data. Removing apostrophes blindly is not a lossless decoder: a source string may
   itself start with an apostrophe, and spreadsheet import/export can transform text. Do not use
   CSV analysis to round-trip canonical identifiers; use JSON or the exact immutable source.

No API, Pydantic, database, TEI profile, or manifest-schema version changes are needed: only the CSV
representation changes, and this ADR records that compatibility decision. Do not regenerate or
rewrite stored export artifacts. Existing download endpoints continue serving their persisted bytes
and checksums; request a new export to obtain the protected representation. Manifest output sizes and
checksums describe the newly generated bytes without changing manifest semantics.

## Consequences

New CSV analysis files favor safe human inspection over raw-text round-tripping. Hazardous cells
have a visible or underlying apostrophe marker, and ordinary text is byte-for-byte unchanged after
CSV parsing. Consumers depending on unprefixed CSV identifiers must use JSON instead. Full quoting
also safely encloses commas, quotes, and embedded CR/LF; quoting alone is not the security boundary.

Regression tests must cover all formula characters, prefix/control variations, optional and free-text
columns, delimiter/newline escaping, deterministic serialization, unchanged canonical records and
JSON, and persisted downloads. Spreadsheet verification must record the tool/version, import options,
and observed text-cell/non-formula behavior; unit tests and documentation research are not visual proof.

### Recorded spreadsheet verification

On 2026-10-04, an isolated headless **LibreOffice 26.8.0.3 680(Build:3)** profile imported CSV
produced by the actual serializer using the explicit settings above. The
[export specification](../08-ingestion-and-export.md#verified-calc-import) records the exact
filter string, official token definitions, input decision table, and repeatable smoke procedure.
Inspection of the converted XLSX with `openpyxl` (`data_only=False`) found 264 string cells and
zero formula cells across a header and 32 canonical records. Hazardous prefixes and genuine
apostrophe-leading values retained their markers. Calc normalized CR/CRLF to LF and XLSX
escaped XML-ineligible controls; decoded contents matched the expected text with that newline
normalization. These observations support the explicit text/non-formula import contract, not
lossless spreadsheet contents, visual rendering, other spreadsheet products, or CSV re-save
safety. The temporary CSV, workbook, and office profile were removed.
